# 0.5.1 — Windows Runtime 慢准备与升级一致性修复

## 问题与修复

0.5.0 在发送 HTTP 响应头前串行运行 OpenCode 模型查询与最近记录定位，可能超过前端 10 秒等待上限。模型准备期间又未登记任务、未建立断线取消，因此会出现前端超时而后端随后启动 Agent 的情况。

- 验证请求与会话占用后立即发送并刷新 NDJSON 响应头，发出 `request.preparing`；只有 Agent 启动阶段才发 `request.started`，不会把连接成功当作 CLI 收到全文。
- 全部预处理失败通过 `envelope` 返回带 requestID/windowID 的 `error` 和 `request.completed`，不静默结束。
- 准备任务纳入 health、取消、停止及会话占用保护。用户取消/断线后阻止 Agent 启动；路径解析等待可立即取消，底层共享 WSL 路径探测仍受原 15 秒超时约束。
- OpenCode 模型目录缓存 5 分钟，按平台、发行版、可执行文件、工作目录和本机可执行文件变更信息区分。并发查询共享任务，单个订阅者取消不影响其他订阅者；最后一个订阅者取消时终止只读查询进程。
- 模型状态目录缓存，最近模型记录每次读取。显式模型不再等待最近记录定位。手动刷新重新读取列表和状态目录，配置改变时失效缓存。
- 使用 spawn 管理进程组；Linux/WSL 本地查询进程组强制终止，Windows 针对确切 PID 使用 taskkill /T /F，绝不按 node.exe 名称批量结束进程。每条查询限时 45 秒，限制输出 8 MiB；菜单为串行查询预留总等待时间。
- 去掉发送前第二次路径同步，配置没变不重复清缓存。
- 协议 7 加入 runtimeVersion、buildID。构建时生成插件期望指纹，Runtime 启动时计算自身指纹，连接时严格比较。部署目录使用完整版本和指纹，避免同版本不同包共用 .complete 标记。旧服务需通过原有身份校验且无任务，才自动停止和替换。

## 验证

- 全套回归：172 项，171 通过，1 项 Windows CMD 专用测试在 Linux/WSL 跳过。
- 真实 HTTP 集成：模型查询等待 11 秒，响应头在 3 秒门限内到达，最终完整结束；准备失败携带完整事件标识。
- 验证取消时查询进程实际退出、断线后不启动 Agent、并发订阅取消隔离、缓存命中后仍跟随新的最近模型、手动刷新重新查询、显式模型跳过 debug paths。
- 验证准备任务阻止无确认停止、强制停止结束准备、同会话准备互斥、审批接口不误取消准备任务。
- 验证协议相同但指纹不一致时拒绝复用，以及同版本不同指纹部署到新目录；Windows CRLF 与 Linux LF 不影响指纹，源码改变则指纹改变。
- 本机真实 OpenCode：207 个模型，最近模型 opencode/space-bunny-free；首轮查询 3550 ms，缓存轮次小于 1 ms（仍读取最近记录）。未调用付费模型。
- 构建、语法、XPI/内置 Runtime 源码一致性与指纹检查通过。未在报告中的 Windows 电脑直接复验；Windows 进程树和安装 UI 仍需现场验证。

## 升级

安装 0.5.1 XPI 并重启 Zotero。运行中任务先停止；设置页启动 Runtime，检查模型准备提示与实际问答。使用外置 Runtime 的用户需同步当前 runtime/src 全部源码，不能只替换 index.js/protocol.js；不匹配的构建会被明确拒绝。首次模型目录查询仍可能较慢，但不会再被误报为后端未启动。

本次为修复代码推送，不自动创建 GitHub Release。报告中的手工 taskkill COMMANDLINE 筛选写法不受 Windows taskkill 支持，勿用该命令批量结束 Node 进程。

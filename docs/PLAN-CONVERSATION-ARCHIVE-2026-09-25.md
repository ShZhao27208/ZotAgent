## 1. 目标与最终边界

由插件自动将结构化聊天保存到 Zotero 原生子笔记。同一主文献的多个窗口和三个 Agent 共用当前一份归档笔记，保留完整可见问答、时间、状态、文献来源和截图。整个归档过程不请求模型、不要求 Agent 生成摘要，不额外消耗 Agent token。

归档笔记只用于保存历史，不自动成为任何 Agent 的输入。需要把历史交给 Agent 时，由用户导出 Markdown 后自行提供。

| 事项 | 最终决定 |
| --- | --- |
| 存储形式 | Zotero 原生子笔记（内部为 HTML），需要时导出 Markdown；不同时维护自动同步的 `.md` 副本 |
| 共享范围 | 同一主文献下的所有对话窗口及 OpenCode、Codex、Claude Code 共用当前归档笔记；不同主文献分开 |
| 首次创建 | 某主文献首次开启对话且没有当前笔记时自动创建；尚未提问时允许为空笔记 |
| 跨次使用 | 关闭窗口或重启 Zotero 后继续上次当前笔记；笔记已删除或不再属于该主文献时创建新的 |
| 切换笔记 | “新建记忆笔记”对同一主文献的所有窗口生效；旧任务仍写旧笔记，新问题写新笔记 |
| 归档时机 | 回答完成、执行失败或用户中断时一次写入；不实时写入、不建立进行中占位记录 |
| 正文 | 问题、选区、完整可见回答；不保存思考过程、推理摘要或原始工具日志 |
| 全文 | 三个 Agent 全部取消插件主动截断；发送完整提取文本，归档仅保存附加说明 |
| 截图 | 保存实际发送的截图及必要来源说明，使用 Zotero 内嵌图片资源以参与原生同步 |
| 排序 | 用户在设置页选择提问时间或结束时间，默认按提问时间从早到晚 |
| 命名 | 设置页下拉菜单组合；默认笔记创建时的“年＋月＋日＋时＋分” |
| 手动收藏 | 保留手动“保存子笔记”，可与自动历史重复；二者不合并、不去重 |
| 无主文献 | 允许普通聊天，明确提示“本次不会自动归档” |
| 终端 | 原生终端不参与自动问答归档 |
| 取消 | 前端立即标记中断并禁止后续阶段；已发送任务调用现有取消接口；不新增后端进程树终止机制 |
| 同步与编辑 | 使用 Zotero 原生同步与编辑能力；不开发笔记编辑历史、合并引擎或自定义云同步 |

## 2. 自动归档行为

### 2.1 主文献与当前笔记

1. 用主文献的库标识和条目 key 区分归档归属，不能仅使用标题或文献 DOI。
2. 归档笔记是主文献的原生子笔记；附加参考文献写入每条记录的来源清单，不因此改变父条目。
3. 所有窗口通过同一个归档协调器查询与切换当前笔记，避免每个窗口各自缓存一个独立目标。
4. 首次创建、重建和手动新建都串行处理，同一文献同时打开多个窗口不得创建重复的当前笔记。
5. 当前笔记映射需要持久化；重启后重新验证笔记存在、未入回收站、库及父条目正确。
6. 笔记标题不能作为唯一身份。用户改名不会导致归档断开；名字相同也不能合并不同笔记。
7. 同一分钟创建多份笔记时，在名称末尾追加序号，如 `2026年09月25日23时20分（2）`。
8. 无主文献时不创建游离笔记、不阻止普通提问。该次提交的“不归档”决定固定，之后切换到文献页不应追认归属。
9. 只读文献库、归档目标被删除等异常应显示准确的归档失败原因，并保留本地可重试的数据；不能静默写到另一篇文献。

### 2.2 提问时冻结归属

在用户提交问题、进入异步全文提取或 Runtime 检测之前，创建不可变的请求快照，至少冻结：

- 请求 ID、窗口 ID、Agent、可用的原生 session ID。
- 主文献与参考文献的身份及显示元数据。
- 当前归档笔记身份；无主文献则记录为空。
- 用户原始问题、发送时选区、截图，以及各文献的全文勾选状态。
- 提问时间、工作目录等本次执行所需信息。

异步提取结果只补充属于本请求的上下文描述，不重新读取其他窗口切换后的笔记目标。全文提取、发送、接收及归档回调使用请求自己的状态，不依赖可被新请求改写的 `this.requestID` 或共享取消标记。

示例：

1. A 窗口的 Claude 请求 Q1、B 窗口的 Codex 请求 Q2 都绑定笔记 N1。
2. 用户点击“新建记忆笔记”，将当前笔记切换为 N2。
3. Q3 在点击后提交，绑定 N2。
4. 即使 Q3 先完成，Q1、Q2 后完成，也分别写入 N2、N1、N1。

创建和切换动作要有确定的先后顺序：新建操作完成后提交的问题必须绑定新笔记；创建失败时保留旧目标并明确提示，不能显示已切换成功。

### 2.3 记录内容与时间定义

| 字段 | 规则 |
| --- | --- |
| 问题 | 保存用户原始问题，不将自动拼接的 PDF 全文存为问题正文 |
| 选区 | 保存提交时的选区文本；能够确定来源时标明来源文献及页码 |
| Agent | 每条回答明确标注 OpenCode、Codex 或 Claude Code；有可靠模型信息时附模型名 |
| 回答 | 保存插件收到的全部可见文本，包含中途可见说明与最终回答；排除内部思考、工具原始结果 |
| 提问时间 | 用户提交该次问题的时间，包含准备阶段 |
| 完成时间 | 收到明确成功完成事件的时间，不将首段输出或网络流关闭当作成功 |
| 中断时间 | 用户点击停止的时间；停止后迟到事件不得把中断改写为完成 |
| 失败时间 | 收到执行失败或确认通信失败的时间 |
| 状态 | 完成、用户中断、执行失败、连接异常；错误有简短说明，不能把失败伪装成完整答案 |
| 文献 | 主文献与全部参考文献的标题、可用作者、年份、DOI、Zotero 条目链接；区分主文献和参考文献 |
| 全文说明 | 每篇文献分别记录提取量、提交量及提交状态，不存全文正文 |
| 截图 | 提交时的图片快照；新截图或清空前端不得影响已提交请求 |
| 内部关联 | 请求 ID、归档笔记 key、排序时间等，使用经过 Zotero 保存往返验证的元数据机制 |

时间内部使用可比较的时间戳及带时区格式，显示默认跟随本地时间并精确到秒。名称默认只精确到分钟，与记录时间精度不同。

没有回答时使用“尚未收到具体回答”。不根据空输出推断 Agent 正在思考；若有明确的运行状态，可附“中断时尚未产生具体回答”，不保存思考内容。

### 2.4 一次性写入、并发与手动编辑

- 仅终态触发记录写入；用户中断即确定归档快照，异步保存不阻塞停止操作。
- 一个请求只归档一次；中断、连接关闭、进程完成同时到达时，以幂等检查防止重复。
- 自动历史保留失败或中断的部分回复；手动收藏由用户选择，原逐条自动保存逻辑不得把失败输出当成成功结果保存。
- 使用每笔记的写入队列，并在写入时读取最新正文。不得用窗口持有的旧整篇 HTML 覆盖其他请求或用户的修改。
- 已完成记录不由缓存重新生成；排序只移动可识别的记录整体，保留其中的用户修改及记录外手写内容。
- 不追踪用户编辑历史，不自动回滚手工删除。无法安全识别记录边界时保留现有内容并提示，不能重建整篇覆盖。
- 实施时验证 Zotero 编辑器与 `saveTx()` 的配合；遇到编辑器未保存内容时避免盲写，延后或提示重试。
- 截图导入或笔记保存失败时显示失败状态并提供重试，同一请求重试不得重复插入正文或图片。
- 归档是一次终态写入，不承诺异常退出前尚未完成的请求能够完整恢复。不要偷偷加入流式落盘或自动恢复的额外范围。
- 同机多窗口并发通过统一队列保证；跨设备同步使用 Zotero 自身机制，不承诺跨设备同时写同一笔记的自定义冲突合并。

### 2.5 排序

设置项提供“按提问时间”和“按结束时间”，均按从早到晚排列，默认前者。结束时间对完成、中断和失败分别使用对应终态时间。

先完成的回答可以先写入；较早提问但较晚完成的记录到达后，应插入正确位置。相同时间使用稳定的请求顺序或 ID 决定顺序，避免反复跳动。

设置改变后重排当前笔记中的可识别记录，其他已切换离开的归档笔记不批量改动。正在运行且绑定旧笔记的请求，仍使用其目标笔记持有的排序规则。由于只在终态归档，笔记不显示“进行中”占位区域。

## 3. 全文发送：所有 Agent 不主动截断

### 3.1 统一规则

删除单篇、参考文献及分别处理路径中所有 `60000` 字符截断逻辑。OpenCode、Codex、Claude Code 都提交用户勾选文献的全部提取文本，不设置 Agent 特例，不提供截断上限设置，不通过摘要替代原文。

完整发送指全部提取文本进入请求；不等同于扫描件已 OCR、不等同于 PDF 所有图像已识别，也不等同于模型已完整理解。

发送前展示各篇提取字符数、预计提交字符数及总量，注明请求体大小、Agent CLI 和模型上下文限制。计数口径需一致，优先按 Unicode 码点计数；请求体限制另按最终 JSON 的 UTF-8 字节计算，不用字符数代替字节数。

### 3.2 固定文案与准确性

成功提交时采用用户确认的格式：

> 已附加 PDF 提取文本：共提取 95320 字符，本次提交全部 95320 字符。
> 提交内容仍受请求体大小、Agent CLI 和模型上下文限制。

准备阶段显示“预计提交全部 N 字符”；不得在 HTTP 被拒绝、CLI 启动失败等情况下虚报已经成功提交给 Agent。根据可观测边界区分“准备完成”“Runtime 已接收”“Agent 进程已启动并提交输入”“执行失败”，不能凭现有过早发出的 `request.started` 事件推断 CLI 成功接收。

异常记录示例：

- 提取完成但准备期间取消：`已提取 N 字符；用户在发送前中断，未提交。`
- 请求体超限：`已提取 N 字符；请求体超过 Runtime 接收限制，提交失败，未主动截断。`
- CLI 启动失败：`已提取 N 字符；Runtime 已接收请求，但 Agent 启动失败。`
- 输入已提交后模型拒绝：保留完整提交数量，并记录模型/CLI 返回的失败原因。
- 未能提取正文：`未提取到 PDF 文本，本次未附加该文献全文。`

不再出现“只发送前 60000 字符”等主动截断文案；也不猜测模型内部丢弃的字符数量。无法确认提交阶段时写“提交状态未确认”。

### 3.3 保留的限制

- Runtime 当前请求体上限为 4 MiB。本轮不无条件提高；超过时在发送前尽可能准确提示并阻止必然失败的请求，不静默删全文、压缩为摘要或丢截图。
- OpenCode 的命令行正文传输改造仍暂缓。移除截断后可能更早遇到命令行长度限制，必须如实显示失败，不以保留旧截断规避。
- Claude/Codex 正文使用 stdin，不存在同一种正文命令行长度问题，但仍受请求体和模型上下文限制。
- 不重新发送已恢复会话的完整历史，不扩大为全局 token 管理或检索系统。

## 4. 前端取消控制

### 4.1 已确认行为

1. 点击停止立即冻结中断时间和已收到的回答，标记请求取消，阻止后续阶段继续执行。
2. 正在提取文本、等待 Runtime 启动或 CLI 检测时，在每个异步边界检查该请求自己的取消状态；不得随后发送 `/v1/run`。
3. Runtime 启动了可以继续运行，不取消 Runtime 服务启动，不关闭其他窗口任务。
4. 已发送的请求调用现有 `/v1/requests/:id/cancel`，并按现有通信机制中止读取；取消操作要绑定请求自己的控制器，避免旧请求取消新请求。
5. 保留中断前收到的输出；迟到输出与完成事件不改写已归档的中断结果。
6. 批处理停止后不启动下一篇；当前已执行子任务按实际状态归档，未启动子任务不伪造回答，可在批次说明中注明未执行数量。
7. 不把用户取消显示成“连接超时”。

### 4.2 明确不做

不新增后端进程树强杀、Windows Job Object、任务调度器、Runtime 停机功能或后台启动取消接口。使用现有服务端取消能力，因此不承诺所有衍生进程立即消失，也不承诺远端已开始的生成立刻停止计费。

归档中断时间是用户操作时间，不伪装成操作系统进程确认退出时间。

## 5. 截图存储与 Markdown 导出

### 5.1 Zotero 原生图片资源

- 保存本次请求实际使用的截图，包括普通截图和长截图。
- 使用当前目标 Zotero 版本支持的笔记内嵌图片/附件导入机制，资源随原生笔记同步。
- 不能将 Runtime 临时路径、绝对本机路径或只在会话内有效的 URL 作为最终笔记图片来源。
- 请求结束清理 Runtime 临时图片，不得删除已经导入 Zotero 的持久资源。
- 截图保存在所绑定的归档笔记下；切换新笔记后旧请求截图也必须进入旧笔记。
- 使用真实 Zotero 验证图片保存后重新打开及跨设备同步；模拟导入成功不等于完成验收。

### 5.2 导出

提供“导出记忆笔记为 Markdown”的用户入口，导出当前选择的归档笔记。优先复用经过验证的 Zotero 能力；若原生路径不能满足图像与格式要求，提供本地确定性转换。

导出必须读取笔记当前正文，包含用户手动修改，不从旧归档缓存重建。保留标题、段落、列表、引用、代码块、链接、表格及图片。图片导出到相对资源目录并在 Markdown 中引用，导出结果移动到其他目录后仍可一起打开。

用户主动导出才创建 `.md` 和图片文件；不后台维护 Markdown 副本，不调用 Agent 转换，不自动把导出内容发送给 Agent。

## 6. 设置与界面

### 6.1 对话窗口

- 显示当前归档笔记名称及归属主文献，可打开对应原生笔记。
- 增加“新建记忆笔记”和“导出记忆笔记为 Markdown”。新建操作同步更新同一主文献的其他窗口。
- 发送前显示全文提取量和预计发送量，不要求多一次模型调用。
- 显示自动归档成功、失败或中断保存状态；无主文献显示固定提示。
- 保留手动“保存子笔记”，用于把精选回答单独收藏，允许重复。
- 原有 `autoSaveNotes` 是独立的旧功能，不充当新归档的开关；本轮不自动打开、不擅自覆盖已有偏好。默认仍关闭，原已启用用户的设置保留。
- 归档异常不覆盖 Agent 本身执行结果：例如应显示“回答完成，归档失败，可重试”。

### 6.2 设置页

位置：`Zotero → 设置 → ZotAgent`，增加“对话历史归档”区域。面向用户的选项由插件偏好管理，不新增 Node Runtime 配置端点。

提供排序下拉菜单以及名称组合器，名称使用笔记创建时的时间。修改名称格式只影响以后新建的笔记，不重命名旧笔记。

名称组合器以多个下拉菜单为主，提供即时预览，避免要求用户学习模板语法。建议实现下列选项集合：

| 维度 | 下拉选项 |
| --- | --- |
| 整体预设 | 中文年月日时分（默认）、中文年月日时分秒、ISO 日期＋时分、ISO 日期＋时分秒、紧凑日期时间、仅日期、文献标题＋日期时间、第一作者＋日期时间、第一作者＋发表年份＋日期时间、文献 key＋日期时间、日期时间＋序号、自定义组合 |
| 日期格式 | `YYYY年MM月DD日`、`YYYY-MM-DD`、`YYYY/MM/DD`、`YYYY.MM.DD`、`YYYYMMDD`、`MM月DD日`、不显示 |
| 时间格式 | `HH时mm分`、`HH时mm分ss秒`、`HH:mm`、`HH:mm:ss`、`HHmm`、`HHmmss`、不显示 |
| 文献字段 | 不显示、标题、短标题（缺失时回退标题）、第一作者、发表年份、DOI、条目 key、第一作者＋年份 |
| 字段顺序 | 日期时间在前、文献在前、前缀＋文献＋日期时间、文献＋序号＋日期时间 |
| 分隔符 | 无、空格、短横线、下划线、竖线、中点 |
| 固定前缀 | 无、ZotAgent、对话记录、研究笔记、文献讨论、自定义文字 |
| 序号 | 仅重名时追加（默认）、始终显示、两位补零、三位补零 |
| 星期 | 不显示、中文星期、中文周、英文缩写 |
| 时间区 | 系统本地（默认）、Asia/Shanghai、UTC |
| 标题长度 | 20、40、60、100 字符、不限制 |

缺失作者/年份/DOI 时有确定的回退，不产生 `undefined`、空分隔符串或空标题。自定义前缀属于必要文字输入，其余通过下拉选择。笔记共用多个 Agent，不使用会随回答变化的“当前 Agent”决定笔记名称。

导出文件名另做操作系统文件名清理，不为了文件名规则篡改 Zotero 中可合法显示的笔记标题。

## 7. 同轮修复范围

### 7.1 历史会话恢复文献

修复 `restoreSession()` 调用 `updateContext(item)` 但后者不接收参数、已有主文献直接返回的问题。增加显式的文献重新绑定入口，恢复正确主文献及可用参考文献信息，清理与原文献不对应的选区和截图。

恢复过程中不允许把正在运行请求的上下文改写；新请求使用恢复后文献的当前归档笔记，已提交请求仍使用其原快照。原文献已删除时，不继续把该会话静默挂在当前另一篇文献上。

### 7.2 分别处理的成功判断

普通发送和批处理共用终态判定：HTTP 流结束不等于成功，必须检查完成事件、退出码、错误和用户取消状态。

每个实际执行的文献子任务分别记录问题、回答和状态，并标明“分别处理”的实际目标文献。归档位置仍是用户提交该批次时主文献的归档笔记，不在批次中途改挂每篇参考文献；单条回答原有收藏路径与新归档区分。

父批次提交时固定归档笔记；批次执行途中点击新建笔记，不应把尚未执行但已属于该批次的问题分流到新笔记。各子任务保留实际开始与结束信息，同一提交时间以子任务序号稳定排序。

### 7.3 Claude 图片输入

修复只传 `--add-dir` 但没有传图片内容或文件身份的问题。基于实际支持的 Claude CLI 输入格式实现图片传递，优先采用明确的图像内容输入；不能把目录授权当成图片已经进入模型输入的证明。

覆盖新会话与恢复会话、普通截图与长截图、文本与图片组合。必要时仅为图片请求采用受支持的结构化 stdin 格式；纯文本路径保持兼容。使用确定性输入测试以及可控的真实视觉验证确认，不仅检查 `supportsImages` 标记。

### 7.4 临时文件清理与文本完整性

- 用显式的“本请求创建文件集合”跟踪临时截图，按实际路径删除，消除 Windows 反斜杠匹配问题。
- 不删除用户提供的文件，不清理其他并发请求仍在使用的文件；正常退出、失败与现有取消路径都覆盖。
- Claude 多文本块不能只 `.find()` 第一个，应保留全部可见文本块及顺序。
- 区分增量与完整文本事件，防止同时处理两种事件而重复回答；工具、思考块不混入回答正文。

### 7.5 明确暂缓

- OpenCode 将 prompt 从命令行改为 stdin/文件的传输重构。
- 文献列表入口未正确选择主附件、参考文献第一个附件未筛选 PDF 的修复；本轮遇到未提取情况必须如实显示，不虚报全文附加。
- 后端进程树强杀及新的取消协议。
- 原生终端自动归档、终端与结构化会话无缝迁移。
- 历史手动选择回传、共享 Agent 输入记忆、自动摘要、思考过程保存。
- PDF OCR、RAG、自动分块检索、全文截断预算设置。
- 大规模无关重构、跨设备自定义冲突合并、笔记编辑历史。

## 11. 后续 GitHub 提交与版本历史规则

### 11.1 用户要求

本次仅写计划，不提交 GitHub。后续每次完整完成一批修改，确认该批次没有已知待修复或待调整项，验证通过后再创建/推送该批次提交。不要在功能未完成时频繁推送中间版本，也不要把阶段清单机械地当成逐项发版指令。

提交并成功推送后，在本地 `docs/VERSION-HISTORY.md` 记录实际提交时间、提交编号和相关信息。不存在本次计划对应的 Git 提交或推送时间，禁止预填、猜测或伪造。

### 11.2 记录字段

建议新增明确区分于“本地可见 Git 历史”的实际推送记录区域：

| 字段 | 内容 |
| --- | --- |
| 批次 | 完整修改批次名称/序号 |
| 版本 | 当时 package/manifest 版本；只有实际发版才写新版本或 tag |
| 提交编号 | 完整 SHA 和便于阅读的短 SHA；多个提交注明范围及最终 HEAD |
| 提交时间 | Git committer 时间，ISO 8601 带时区；可另列 author 时间但不得混用 |
| 推送完成时间 | 本次真实成功推送后记录的本机时间，默认 Asia/Shanghai；不得用作者时间推算 |
| 远端目标 | 实际 remote、分支和确认后的远端 HEAD |
| 主要改动 | 功能与修复摘要、对应本计划的完成项 |
| 验证 | 测试、构建、真实环境结果及尚存限制 |
| 产物 | 若实际构建分发包，记录路径及必要校验信息；没有则不编造 |

### 11.3 与现有脚本、hook 的兼容

当前 `scripts/update-version-history.mjs` 会重新生成整个 `VERSION-HISTORY.md`，`.githooks/pre-push` 又会运行它并要求提交文件变化。直接在文件末尾人工追加真实推送记录，下一次生成可能丢失；同时，推送完成时间只能在推送后知道。

因此在后续首次需要推送的完整批次中处理以下维护任务，本次不修改这些脚本：

1. 让生成器保留独立的“实际推送记录”区域，或从稳定的结构化记录来源重建该区域；不覆盖人工/自动记录的真实推送结果。
2. 调整 pre-push 检查，使其兼容“完成验证 → 提交/推送 → 本地记录推送结果”的时序，不要求把尚未发生的推送成功时间提前写入。
3. 保留有价值的检查，不以直接禁用 hook 代替修复，不形成每写一条推送记录又必须立刻为它单独推送的无限循环。
4. 实际推送成功且远端 HEAD 核对后，追加本地记录。该条推送后记录可以留作本地修改，并随下一次完整批次纳入版本管理；用户本次要求的是推送后在本地记录，不要求为了记录自身立即再次推送。
5. 推送失败时不写成功记录，不将仅存在本地的提交标记为 GitHub 已有。若结果未知，先核对远端状态再判断。
6. 将用户已有但未提交的其他变更与本批次区分，只暂存本批次明确涉及的文件。
